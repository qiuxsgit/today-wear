# Commit Code Skill

## 角色设定

你是 **Git 提交管理专家**，负责智能分析代码变更、生成规范的提交信息、执行精准的代码提交操作。

---

## 触发场景

| 用户说法 | 行为 |
|---------|------|
| "提交所有代码" / "全部提交" / "commit all" | 检查所有待提交内容，一次性提交 |
| "提交 xxx 功能的代码" / "把 xxx 相关的提交了" | 筛选该功能相关文件，只提交相关变更 |
| "提交 xxx 模块的代码" | 筛选该模块目录下的变更 |
| "提交并推送" | 提交后自动执行 git push |

---

## 工作流

### 步骤一：获取当前 Git 状态

**操作**：
1. 执行 `git status` 查看所有变更
2. 执行 `git diff --stat` 查看变更统计
3. 如果有已暂存的文件，执行 `git diff --cached --stat`

### 步骤二：判断提交模式

#### 模式 A：提交所有代码

**条件**：用户说"提交所有代码"、"全部提交"、"commit all"

**操作**：列出所有变更文件，按模块分组展示，确认后全部暂存并提交。

#### 模式 B：按功能筛选提交

**条件**：用户说"提交 xxx 功能的代码"、"把 xxx 相关的提交了"

**操作**：
1. 从用户描述中提取**功能关键词**
2. 分析每个变更文件与该功能的关联度
3. 只展示相关文件，无关文件不处理

**功能关联度判断规则**：

| 判断依据 | 权重 |
|---------|------|
| 文件路径包含功能关键词 | 高 |
| 文件名包含功能关键词 | 高 |
| 变更内容中包含功能关键词 | 中 |

#### 模式 C：按模块筛选

**条件**：用户说"提交 xxx 模块的代码"

**操作**：根据目录筛选对应模块的变更。

### 步骤三：确认提交范围

向用户展示即将提交的文件列表，说明筛选依据，等待确认。

### 步骤四：生成提交信息

1. **分析变更类型（type）**：

| 变更特征 | type |
|---------|------|
| 新增文件为主，实现新功能 | `feat` |
| 修改现有代码，修复问题 | `fix` |
| 代码结构变化，功能不变 | `refactor` |
| 只修改注释/文档 | `docs` |
| 只新增/修改测试代码 | `test` |
| 构建/配置/依赖变更 | `chore` |

2. **推断 scope**（按变更文件路径映射到模块目录）：

| 文件路径前缀 | scope |
|------------|------|
| `lib/database/` | `database` |
| `lib/models/` | `models` |
| `lib/repositories/` | `repositories` |
| `lib/screens/` | `screens` |
| `lib/widgets/` | `widgets` |
| `lib/services/` | `services` |
| `lib/theme/` | `theme` |
| `lib/l10n/` | `l10n` |
| `lib/main.dart` | `app` |
| `test/` | `test` |
| `pubspec.yaml`、`pubspec.lock` | `deps` |
| `CLAUDE.md`、`.claude/` | `rules` |
| `*.md`（文档类） | `docs` |
| `analysis_options.yaml`、`l10n.yaml` 等配置 | `chore` |

- **单模块变更**：scope = 该模块名
- **跨多模块变更**：scope = 主导模块（变更行数最多 / 业务根因所在），其余模块在详细说明中提及
- **跨 3+ 模块且无明显主导**：可省略 scope，写 `<type>: <描述>`

3. **提交信息格式**：
   ```
   <type>(<scope>): <简短描述>

   <详细说明>（可选）

   Co-Authored-By: Claude Opus 4.6 <noreply@anthropic.com>
   ```

### 步骤五：执行提交

1. 暂存相关文件：`git add <files>`（不使用 `git add .`，明确指定文件）
2. 执行提交：`git commit -m "<message>"`
3. 如果用户说"提交并推送"，执行 `git push`
4. 输出提交结果

## 特殊场景处理

### 场景一：没有变更

告知用户当前没有待提交的变更。

### 场景二：存在未跟踪的新文件

- 明确告知用户哪些是新文件
- 确认是否需要纳入版本控制
- 对于敏感文件（`.env`、密钥等）警告用户不要提交

### 场景三：变更文件过多

- 按模块分组展示
- 建议用户考虑分多次提交
- 询问是否需要按功能拆分

### 场景四：用户筛选的关键词无匹配

告知未找到匹配文件，列出当前所有待提交文件供参考。

### 场景五：分支安全确认

仅在以下情况主动提醒：
- **当前分支是 `main`**：提醒通常不应直接提交到 main
- **未识别的分支**：列出分支名让用户确认

## 注意事项

- **先确认再提交**：永远不要在未确认的情况下执行提交
- **明确文件列表**：不使用 `git add .`，逐个指定文件
- **敏感文件警告**：发现 `.env`、密钥文件等敏感内容时警告用户
- **分支安全**：不在 main 分支执行 force push
- **提交粒度**：建议一个提交只做一件事，鼓励用户拆分大提交
- **不使用** `--no-verify`、`--amend`
